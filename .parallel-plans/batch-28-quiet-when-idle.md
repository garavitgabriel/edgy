## Why
Measured on the Mac mini (2026-11-09): Edgy sat at ~19% of a core and ~2,700 wakeups/s with a window open and idle, and still ticks 30×/s with no window. `sample` shows SwiftUI laying out the mirrors every frame. The pointer-guard event tap and the touch callback share the main thread with that work, so the whole system's pointer waits on Edgy's drawing. Gabriel also reports "Settings freezes" and an empty app list in the App chooser.

Already on `main` (chief): `SettingsModel.takeDecisions()` and `receive(_:)` no longer write unchanged values.

## Build
1. **Measure first.** `scripts/measure-idle.sh`: for the running Edgy, print CPU % and wakeups/s averaged over 20 s (`top -l`), and exit non-zero over a budget passed as arguments. Record the "before" numbers in the done report for: no window; popover open; Settings open; Settings open with the App chooser popover open; onboarding open. (Gabriel or the chief runs the live states; give exact steps.)
2. **Event-driven overlay.** `OverlayController` stops its clock when the timeline is empty and no display check is up, and starts it when a decision arrives (observe the model, or have the feed wake it). No repeating timer while idle. `LiveScreens`/`placements()` are read when a plate appears or the screens change, never per tick. Fades stay smooth (same 200 ms).
3. **Views redraw only on real change.** Find every per-frame write to observed state in your folders and stop it (compare before assigning). Mirror data (`mirrorCatalog`, `mirrorZones`, `catalogByCategory`, `availability(of:)`) is computed once per `model.revision` / engine-status change and cached, not per body evaluation. `LiveBrightnessOutput.builtInDisplay()` is cached and refreshed on display reconfiguration.
4. **Input off the main thread.** The pointer-guard event tap (`TouchKit/LiveSystem.swift`), the multitouch callback scheduling (`MultitouchBridge.swift`) and the key-recorder / switcher taps (`Actions/LivePickers.swift`) run on a dedicated input thread's run loop, so Edgy's drawing can never delay a pointer event. Keep every existing ordering guarantee; protect shared state; hop to main only for UI. Re-enable a tap on `tapDisabledByTimeout` / `tapDisabledByUserInput` and log it once. If the gesture pipeline's threading contract (EdgyCore/Gestures) blocks this, write the blocker with the smallest contract change that would unblock it and do items 1–3, 5–6.
5. **App chooser shows an empty list** (Gabriel's screenshot: Open App → "Choose an app" → the popover has the search field and nothing under it). Reproduce it live first and write down the cause; suspects: the list is loaded by the field's `.task` and never reaches the open popover; ~200 non-lazy rows each loading an icon synchronously on the main thread while the parent re-renders. Fix so the list appears within 300 ms of opening on a Mac with 300 apps: load on open (as `AddAppView` does), show "Loading apps…" in `ink2` until it arrives, lazy rows with stable IDs across the two sections, icons loaded off the main thread and cached. Same fix wherever the list is used (add-app, chips). Test with a 300-app fake provider and a slow provider.
6. **Batch 26 follow-ups (backlog):** no `gestureCaught` tick and no `actionRan` for a switcher slide until it opens (Router); `switcherAppCount()` moves to the opening; settings-reference notes that sensitivity scales the opening travel.
