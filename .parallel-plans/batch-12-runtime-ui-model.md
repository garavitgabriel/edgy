# Batch 12 — EDGY-RUNTIME-2: the model the settings window binds to

Read `CLAUDE.md`, `.parallel-plans/2026-11-07-edgy-v04.md`, then `done-batch-6.md` and `done-batch-9.md`. You own `Sources/EdgyRuntime/**`, `Tests/EdgyRuntimeTests/**`, `docs/settings-reference.md`. The window's design isn't final; its **bones** are (see the shared brief). Build models, not views. Prefer plain observable state the app can wrap (callbacks on main, value snapshots); don't import SwiftUI.

## Build

1. **Profile overrides.** `EdgyConfig.profile(for:)` now resolves inheritance (contract). Make the runtime use the resolved profile everywhere (engine, router, enabled/slide/longPress zones, validation of the effective profile). In `SettingsEditor`: `addAppProfile` creates **inheriting** profiles by default (keep the old copying path available, documented); API to override one gesture for an app, to turn one off for an app (`doNothing`), and to revert an override back to the default; a query returning the effective bindings for an app with a source per row (`inherited` / `overridden` / `turnedOff` / `appOnly`). Undo/redo covers all of it.
2. **Validation for v0.4.** `doNothing` is compatible with every zone/gesture (validator + `compatibleActions` list it, last). Modifier-only `KeyCombo` is valid only for `keyboard.hold` (`invalidKeyCombo` elsewhere, with a reason). Inheriting app profiles validate their overrides (no `duplicateBinding` against the default they replace). **Conflict notes** with a new severity `.info` (document; keep existing codes stable): `tapWaitsForDoubleTap` when a zone has both tap and double-tap (the tap waits the double-tap window — say how long), and `holdAndTriggerOnLongPress` if that combination is possible; notes appear in `issues` but never block saving.
3. **Engine context.** Pass `doubleTapZones` (zones with a double-tap bound in the effective profile) in `GestureContext`.
4. **Live feed + Test Mode.** A main-thread, throttled (≤ 60 Hz for touches, events unthrottled) feed from `Engine` for the mini trackpad mirror and Test Mode: per device, normalized touch positions with id and state (`down`, `claimed`, `rejected`); decisions — gesture recognized (zone, kind, phase), rejected (contact, zone if known, `RejectionReason`), action ran / failed (message) / unavailable (reason) / would run (Test Mode). Subscribing is opt-in and costs nothing when nobody listens. **Test Mode** (`Engine.setTestMode(_:)`, not persisted): the pipeline and router run normally, actions are not performed (holds get no down/up), haptics still give the "caught" tick so the user feels recognition, and the feed reports "would run <action>". Turning Test Mode off mid-gesture is safe.
5. **Availability observers.** `refreshAvailability()` notifies observers when anything changed (a `SettingsChange` cause or a separate callback — document).
6. **Customization audit.** Write `docs/settings-reference.md`: every `AppSettings` and `GestureSettings` field, every catalog action with its parameters (kind, range/choices, default, display name), per-binding cross-cutting parameters (`haptics`, `sensitivity`), and profile features — each with how the UI changes it (`SettingsEditor` method). Back it with a test that walks every `AppSettings`/`GestureSettings` field (via a mirror or an explicit exhaustive list that fails when a field is added) and every catalog parameter, asserting each is settable through `SettingsEditor` and survives save/reload.
